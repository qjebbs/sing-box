# 节点评分

一个组如何把[健康检查](/zh/configuration/shared/health-check/)的结果变成它挑选节点的依据，以及每一部分为什么是这个形状。

本页讲的是理由，不是字段：可配置项见[负载均衡](/zh/configuration/outbound/loadbalance/)和
[URL 测试](/zh/configuration/outbound/urltest/)。

### 两个问题

一个节点可以以两种彼此独立的方式不好，而一个组只需要回答其中一个：

- **离我多远？** 170ms 的节点比 40ms 的节点拖慢它承载的一切。
- **有多稳？** 一个平时 200ms、偶尔卡三秒的节点，会让恰好落在那次卡顿上的流量变慢。

`quick` 回答第一个，`steady` 回答第二个。这就是它们不是一个分数配一个权重的原因：
没有“一次卡顿值多少延迟”的模型，任何权重都不比另一个更好；而需要猜的权重，是没有测量支持的数值。

### 统计量

每个统计量都只用**成功**的检查计算。失败的检查等满了超时，它的延时说明不了节点在正常时的延时：
失败的比例被单独携带，在生成分数的地方混入。

记 `x₁ … xₙ` 为成功检查的延时，`n` 为其数量：

```
MED     = median(x₁ … xₙ)
JIT     = 1.4826 × median(|xᵢ − MED|)
DEV     = (1/n) × Σ|xᵢ − MED|
```

只有 `MED` 表达节点远近。`JIT` 与 `DEV` 度量的是同一件事的两种汇总方式：每次检查偏离该节点自身中位数多少。
两者都以节点自己的中位数为基准，因此都不含远近——稳定在 4s 的节点和稳定在 100ms 的节点，抖动是一样的。

- **`MED`** 取中位数而不是平均值。平均值会被单次慢速检查拉走，于是它描述的是窗口里最差的那一刻，而不是节点。
- **`JIT`** 是这些偏差的**典型**值，即中位数。单次慢速检查拉不动它：它必须先越过样本的中间位置。
  `1.4826` 把偏差的中位数换算成标准差的估计，使 `JIT` 与 `DEV`、以及下面的标准误处于同一尺度
  （正态样本下 `MAD ≈ 0.6745σ`，见下文“为什么不用标准差”）。
- **`DEV`** 是这些偏差的**平均**值。每次检查按自己的份额计入，因此偶发的尖峰不会被忽略，重复出现则累加。

两者回答的是同一批偏差的不同问题，这正是两个目标的全部区别：

| | 问题 | 结论 |
| --- | --- | --- |
| `JIT` | 它通常波动多少？ | 卡过一次的节点仍然是近的节点 |
| `DEV` | 它总共多付了多少？ | 会卡的节点不是稳的节点 |

### 分数

```
cost  = MED + JIT    # quick，节点通常的代价，毫秒
cost  = DEV          # steady，它偏离自身典型值多少，毫秒
```

两个分数都以毫秒计，但含义不同，它们对应开头的两个问题：

- `quick` 是**节点通常的代价**。一个很近但不稳定的节点，和一个单纯更慢的节点，代价一样，
  所以 `JIT` 按自身尺度加一次。写成乘积是同一件事，而且能看出“加”的含义：

  ```
  MED + JIT = MED × (1 + JIT / MED)
  ```

  括号里是**相对抖动**：`quick` 按远近排序，再按该节点的典型波动修正。

- `steady` 只取 `DEV`，不含 `MED`。它问的是“这个节点偏离自己典型值的绝对量有多大”，
  因此一个 4s 但稳定在 4s 的节点，和一个 100ms 但稳定在 100ms 的节点，同样稳。
  名字就是这个问题本身：不问它有多快，只问它有多稳。

失败按自身占比混入，并按节点自身的尺度度量：

```
failure = min(TIMEOUT, 3 × cost)
score   = (ALL - FAIL) / ALL × cost + FAIL / ALL × failure
```

一次失败相当于三次成功：它毕竟需要重试，但它按节点自身的尺度计分，而不是按等满的超时。
若按超时计分，一个很快但失败过一次的节点会被埋在所有从未失败的节点之后，无论延时如何；
以 `TIMEOUT` 为上限，则保证“大部分时候失败”的节点不会因为它就是在失败而排得更靠前。

### 容差

组不会为它无法信任的差异切换。区间是最优节点周围“视为同样好”的范围，两个目标各有一个，
因为它们的**量**不同——这正是两个字段不能合并的原因：

| 目标     | 分数        | 字段               | 单位             | 默认   |
| -------- | ----------- | ------------------ | ---------------- | ------ |
| `quick`  | `MED + JIT` | `rtt_tolerance`    | 相对最优值的比例 | `0.2`  |
| `steady` | `DEV`       | `jitter_tolerance` | 绝对毫秒         | `10ms` |

一个容差只属于衡量它那个量的目标：把它用在另一个目标上，或用在一个留着默认值的目标上，
会在创建组时被拒绝，而不是被静默忽略——没有效果的值是错误，不是偏好。

**延时用相对值**，因为它离 0 很远：最优 170ms 的 20% 是 34ms，是一个实在的带宽。

**抖动必须用绝对值**，因为它趋近 0：最优 2.8ms 的 20% 是 0.56ms，比延时的存储精度大不了多少，
而实测的 2σ 分辨率是 6.6ms——**一个 0.56ms 的带宽选出的是噪声，不是节点**（推导见下文“噪声”）。
所以抖动的带宽是一个可以直接理解的绝对量：`jitter_tolerance: 10ms` 就是“与最稳的节点相差 10ms 以内，
都算同样稳”。

`steady` 的区间还要加上一份**分辨力余量**：

```
band = jitter_tolerance + 2√2 × DEV_best / √n
cut  = DEV_best + band
```

第二项不是“有时才生效的下限”，而是始终附加的余量——因为 `jitter_tolerance` 描述的是**真实差距**，
而比较只能看到**观测值**：

| `sampling` | 余量 | 带宽（`jitter_tolerance: 10ms`） |
| --- | --- | --- |
| 10 | 2.5ms | 12.5ms |
| 50 | 1.1ms | 11.1ms |
| 200 | 0.6ms | 10.6ms |

采样越多，余量越小、带宽越接近配置值，但**永远不会窄于它**。

为什么是相加而不是取较大者：若取 `max`，在 `jitter_tolerance`（10ms）明显大于余量（2.5ms）时，
余量等于不存在，切点上的节点会按测量噪声每轮进出——实测一个真实 DEV 恰在切点上的节点，
入选率正好 50%。相加把切点外推一个余量，同一个节点稳定在 74%。

余量用 `DEV_best` 而不是每个节点自己的标准误，否则“越吵的节点余量越大、越容易被入选”，方向相反。

`quick` 不需要这一项：实测最优节点 408ms 时带宽 81.6ms，而分数本身的 2σ 噪声约 1.8ms，
只占 2.2%，可以忽略。

### 连接保留

在用节点被替换时，它已有的连接不一定被中断。刚离开选择的节点，只要超出区间的部分仍在两个估计的噪声之内，就会被保留，
以免因为一次本可以朝任意方向变化的测量而断开连接。容许量以区间本身为上限，因此节点最多存活到距最优两倍容差处。

这是为连接做的迟滞，与选择是两个问题：选择问的是“新连接该用哪个节点”，保留问的是“值不值得断掉某个节点已有的连接”。

### 噪声

这里的每个统计量都是小窗口上的估计，因此每次比较都有误差。`n` 个样本的均值的标准误是 `σ/√n`，
而 `DEV` 是一批偏差的均值，这些偏差自身的离散度大约就是 `DEV`：

```
SE(DEV) ≈ DEV / √n
```

**相对噪声是 `1/√n`，与节点无关，只取决于样本数。** 实测（`sampling` 10，10 个节点的原始样本）
各节点的 `SE(DEV)/DEV` 落在 24%~38%，而 `1/√10 = 32%`，与推导一致。

比较两个节点所需的分辨力是差值，两个独立估计各贡献一份，取 2σ 后约为 `2√2/√n`：

| `sampling` | 相对分辨率 `2√2/√n` | 若用 20% 的相对带宽 |
| --- | --- | --- |
| 10 | 89% | 比噪声窄 4.5 倍 |
| 50 | 40% | 比噪声窄 2 倍 |
| 200 | 20% | 恰好持平 |
| 500 | 13% | 带宽生效 |

这就是**抖动用绝对值、延时用相对值**的根本原因。要让 20% 的相对带宽具备意义，需要
`sampling > 200`；在 `interval` 为 2 分钟时那是 400 分钟（约 6.7 小时），
而窗口越长，读到的越是过去——**降低噪声与跟上变化是同一个旋钮的两端。**

换成绝对的 `jitter_tolerance` 之后，这个问题消失：带宽是一个配置值，不随样本数缩水，
而余量始终附加、并随样本数收缩（见上文“容差”的表），因此不存在“采样不足就退化成追噪声”的阶段。

!!! note ""

    需要澄清一个常见的直觉：**噪声不能被“剔除”**。`SE(DEV)/DEV = 1/√n` 对所有节点是同一个比例，
    从每个节点的 `DEV` 里减掉它，等于全体乘以 `√(1−1/n)`——排名与选择完全不变。
    噪声不是偏置（可以减掉），而是围绕真值的波动（减不掉）。能被减掉的只有它在**带宽**里的体现，
    也就是上面的分辨率项。

### 为什么不用标准差

样本标准差是度量离散度的常用做法，但在这里不合适，三个原因叠加：

1. **它以平均值为中心，而平均值会被离群值拉走。** 十次检查里一次慢速，均值从 449ms 抬到 897ms，
   剩下九次的偏差就被拿去和一个与它们无关的中心比较：它们 457ms 的偏差变成了 751ms，而它们一个都没变。
2. **它有平方，于是一个样本可以主导结果。** 在某个窗口里一次检查用了 3.15s，83% 的方差来自那一次，
   报告出来的离散度描述的是那一次探测，而不是节点。
3. **开方并不能把尺度还原。** `n` 个样本中一个 `X` 的尖峰，对平均偏差的贡献是 `X/n`，
   这正是它拖慢的连接份额；但对标准差的贡献是 `X/√n`——`n = 10` 时就已经高估 3.2 倍，窗口越长越离谱。

`DEV` 是同一个想法去掉这两个缺陷：线性，且以一个尖峰无法移动的中心为基准。在 200ms 与 800ms 之间来回的节点仍然读出 445ms，
所以不是说 `DEV` 忽略了不稳定——而是这个估计始终在描述节点。

### 为什么不用趋势

窗口是有顺序的，而上面所有统计量都没有用到它：把样本打乱，`MED`、`JIT`、`DEV` 都不变。
因此一个已经持续变差十分钟的节点，只要离散度相同，读数和一个稳定的节点一样。

半窗对比（`median(后半) − median(前半)`）确实能恢复这一信息，而且代价很低。它没有进入分数，是因为含趋势的分数会让
`interval` 变化时排名也变化，而排名必须是节点自身的性质，不是它被采样的节奏的性质。趋势属于决策，与容差并列，不属于测量。

它也需要小心：`sampling` 为 10 时，后半窗五个样本里连续两次异常并不能推动它的中位数，因此趋势要到第三次才会出现。
这使它成为一个比“最近一次检查”更慢的信号，而后者本来就在统计量里。

### 调试评分

一个组的完整报告——每个统计量、每个节点、以及计算它们的原始检查——由 Clash API 的
`GET /private/health/{tag}` 提供，因此排名可以被离线重放和解释，而不是从日志里推断。

报告描述的是同一次排名，并且带够了重放所需的信息：`best` 是其它节点用于比较的那个节点，
`limit` 是仍然算作同样好的最高分数。一个节点的 `status` 与 `best` 相同、且 `score` 不超过
`limit` 时，就与 `best` 同样好。负载均衡组把这样的节点全部选上（或至少 `min_nodes` 个），
而只用一个节点的组会在它仍属于其中时保持不动，因此在那里 `best` 与 `selected` 可能指向不同
的节点。这些字段全部来自同一轮检测，因此在一轮检测进行中取到的报告，看到的是那一轮的排名，
而不是“已测完的节点”与“上一轮决策”的混合。
