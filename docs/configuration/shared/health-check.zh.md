### 结构

字符串或对象。

当为字符串时，为顶层 [`health_checks`](/zh/configuration/#health_checks) 选项中定义的共享健康检查的标签。

当为对象时：

```json
{
  "interval": "5m",
  "sampling": 10,
  "url": "https://www.gstatic.com/generate_204",
  "idle_timeout": "30m",
  "relay_path": [
    "proxy-a",
    "proxy-b"
  ]
}
```

健康检查用于检查并为出站组提供节点的健康状态信息，可被多个出站组共享，避免重复的健康检查开销。

出站组承载的连接也会被关注：通过检查却丢掉流量的节点不会被信任到下一次定时检查——在短时间窗口内出现若干次连接失败后，该节点会被重新检查。重新检查会替换其最近一次结果而不是新增一条，因此所有节点的结果仍保持与检查间隔一致的均匀采样。

顶层 `health_checks` 的每一项使用相同的对象结构，并额外带有 `tag` 字段：

```json
{
  "health_checks": [
    {
      "tag": "default",
      "interval": "5m",
      "sampling": 10,
      "url": "https://www.gstatic.com/generate_204"
    }
  ]
}
```

!!! warning ""

    每个出站组都必须显式配置健康检查，不存在隐式的默认健康检查。

### 字段

#### interval

每个节点的健康检查间隔。不小于 `10s`，默认为 `5m`。

#### sampling

对最近的多少次检查结果进行采样。大于 `0`，默认为 `10`。

#### url

用于健康检查的链接。默认使用 `https://www.gstatic.com/generate_204`。

!!! note ""

    检查只在该组被使用时进行：从未被使用的健康检查不会执行任何检查。
    首次使用会启动检查循环，并立刻执行一轮。

#### idle_timeout

没有任何出站组使用此健康检查后，暂停健康检查的时长，`0` 表示持续检查。

当一个共享健康检查被多个出站组使用时，只有在所有组都空闲该时长后才会暂停检查。

暂停期间不会测试任何节点。只要有组再次被使用就会立即恢复检查，并立刻进行一次检查以刷新统计，
因为早于 `(sampling+1) * interval` 的结果会被丢弃。

小于 `interval` 的值会被提升为 `interval`。

#### relay_path

以被检查节点为入口，以中继方式进行健康检查。

限制：由于入口以外节点不能是出站组，这里不支持 `selector`, `loadbalance` 等出站组。

假设入口是一个出站组，你配置有链式代理如下：

```json
{
  "tag": "relay",
  "type": "relay",
  "outbounds": ["入口组", "中转", "出口"]
}
```

则实际链路为： `入口组的某个节点` -> `中转` -> `出口`

你希望健康检查链路与上图一致，那么只需配置入口以外的节点：

```json
"relay_path": ["中转", "出口"]
```

实际检查链路为： `入口组被检查节点` -> `中转` -> `出口`

若非如此，几乎不可能检测出这样的节点，它们直接使用没问题，但作为 relay 的上游时，却由于审计规则等原因，无法正常工作。
配置此项还可以避免服务器对测试请求的劫持，提高检测的准确性。

### 推荐配置

负载均衡的 `quick` 与 `idle` 目标的排序依据是最近 `sampling` 次检查，窗口跨度为 `interval × sampling`。建议：

| 场景 | `interval` | `sampling` | 跨度 |
| --- | --- | --- | --- |
| 日常负载均衡（推荐） | `2m` | `10` | 20 分钟 |
| 节点少、探测成本低 | `1m` | `15` | 15 分钟 |
| 节点多、希望更稳 | `2m` | `15` | 30 分钟 |
| 默认值，探测受限（跨度超出建议） | `5m` | `10` | 50 分钟 |

负载均衡的采样数不少于 10 个，窗口跨度不超过 30 分钟。

`urltest` 只用一个节点，窗口取 10 分钟即可，不必为了样本数拉长跨度：

| 场景 | `interval` | `sampling` | 跨度 |
| --- | --- | --- | --- |
| 推荐（探测次数减半） | `2m` | `5` | 10 分钟 |
| 希望更快发现变化 | `1m` | `10` | 10 分钟 |

两者跨度相同，实测的单节点同选率差别在噪声内。`2m × 5` 的代价是窗口里只有 5 个样本：中位数更粗，band 的分辨率余量按 `1/√n` 放宽约四成，而且任何变化最晚要 2 分钟才被看见——检查间隔本身就是反应粒度。跨度超过 10 分钟之后，窗口选出的节点与它此后的表现明显更容易对不上。

`max_fail` 保持 `0`：`idle` 的分数确实把失败计入，但一次失败只算一次坏检查——10 个样本时是 50 分，正好一个 `tolerance`，而 band 还要再加分辨率余量，所以单次失败推不动它。允许失败时，真正拦住节点的是 `max_fail` 这道状态闸门。`tolerance` 保持默认。
